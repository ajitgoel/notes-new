🗂 The Standard File Layout

Terraform doesn't enforce a file structure, but the community has converged on one. Every project you touch will follow this pattern:

my-infra/
  ├── main.tf        # core resources — what you're building
  ├── variables.tf   # input declarations (no values here)
  ├── outputs.tf    # values to export after apply
  ├── providers.tf  # provider config & required_providers
  ├── locals.tf     # computed/derived values (optional)
  ├── terraform.tfvars # actual values — gitignored for secrets
  └── .terraform.lock.hcl # provider lock file — commit this
Convention

For a root module < 300 lines, everything can live in main.tf. Split into separate files as soon as it becomes hard to scan. Terraform sees all .tf files in a directory as one configuration — file names are purely organizational.

🧱 The Four Block Types You Must Know

HCL is built around blocks. There are four you'll use constantly:

terraform {}

Required version constraints, backend config, and required_providers. One per project.

provider {}

Configures a provider (azurerm, aws, google). Credentials, subscription ID, default tags.

resource {}

Declares an infrastructure object to create/manage. This is 80% of your code.

data {}

Read-only lookup of existing resources. Doesn't create anything — fetches IDs and attributes.

providers.tfterraform {
  required_version = ">= 1.6.0"

  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 3.100"   # ~> means: >= 3.100, < 4.0
    }
  }

  backend "azurerm" {
    resource_group_name  = "rg-tfstate"
    storage_account_name = "empowerpmsstate"
    container_name       = "tfstate"
    key                  = "dev/empower-pms.tfstate"
  }
}

provider "azurerm" {
  features {}  # required even if empty
  subscription_id = var.subscription_id
}

🔤 HCL Types & Expressions

Terraform's type system is simple but strict. Know these cold:

variables.tf# Primitive types
variable "environment"  { type = string }
variable "node_count"    { type = number; default = 3 }
variable "enable_https"  { type = bool;   default = true }

# Collection types
variable "allowed_ips" {
  type    = list(string)
  default = ["10.0.0.1", "10.0.0.2"]
}

variable "tags" {
  type = map(string)
  default = {
    Environment = "dev"
    Owner       = "platform-team"
  }
}

# Object type — structured, typed
variable "aks_config" {
  type = object({
    vm_size    = string
    node_count = number
    zones      = list(string)
  })
}

🔗 References & Expressions

Terraform builds an implicit dependency graph from references. When you reference one resource in another, Terraform knows to create the first one first — no depends_on needed in most cases.

main.tfresource "azurerm_resource_group" "main" {
  name     = "rg-empower-${var.environment}"   # string interpolation
  location = var.location
  tags     = var.tags
}

resource "azurerm_key_vault" "main" {
  name                = "kv-empower-${var.environment}"
  location            = azurerm_resource_group.main.location  # reference!
  resource_group_name = azurerm_resource_group.main.name       # reference!
  tenant_id           = data.azurerm_client_config.current.tenant_id
  sku_name            = "standard"
}

# data source — reads existing AAD config, creates nothing
data "azurerm_client_config" "current" {}
Reference Pattern

The reference syntax is always: TYPE.NAME.ATTRIBUTE — e.g. azurerm_resource_group.main.name. For data sources it's data.TYPE.NAME.ATTRIBUTE. Memorize this.

📤 Outputs & Locals

locals.tf + outputs.tf# locals.tf — computed values, referenced as local.<name>
locals {
  name_prefix = "empower-${var.environment}"
  common_tags = merge(var.tags, {
    ManagedBy = "Terraform"
    UpdatedAt = timestamp()
  })
}

# outputs.tf — values exposed after apply
output "resource_group_id" {
  value       = azurerm_resource_group.main.id
  description = "Resource group ARM resource ID"
}

output "key_vault_uri" {
  value     = azurerm_key_vault.main.vault_uri
  sensitive = true   # redacted in terminal, still in state
}

⚡ The Core Workflow

terraform init

Downloads providers, initializes backend. Run once per project, and again when providers change.

terraform plan

Shows what will change. The + / ~ / - output is your diff. Always review before apply.

terraform apply

Executes the plan. Prompts for confirmation unless -auto-approve. Never use auto-approve on prod.

terraform destroy

Tears down everything in state. Use -target to destroy a single resource selectively.

State is sacred

Terraform's state file is the source of truth about what it manages. It maps your HCL to real cloud resources. Never edit it manually. Store it remotely (Azure Blob Storage). Lock it to prevent concurrent applies.
