📥 Variables: Full Anatomy

The variable block is the public API surface of your module. Every attribute matters for production-grade configs:

variables.tfvariable "environment" {
  type        = string
  description = "Deployment environment: dev, staging, prod"

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment must be dev, staging, or prod."
  }
}

variable "location" {
  type    = string
  default = "westus2"
}

variable "aks_node_pool" {
  description = "AKS system node pool configuration"
  type = object({
    vm_size    = string
    node_count = number
    os_disk_gb = optional(number, 128)  # TF 1.3+: optional with default
  })
}

variable "sql_admin_password" {
  type      = string
  sensitive = true   # redacted in plan/apply output and logs
}

🔢 Variable Precedence (last wins)

1default in the variable block — lowest precedence
2terraform.tfvars — auto-loaded if present
3*.auto.tfvars — auto-loaded, alphabetical order
4-var-file="prod.tfvars" — explicit CLI flag
5-var="key=value" — individual CLI override
6TF_VAR_name — environment variables — highest precedence

⚙️ Locals: Internal Derived Values

Locals are computed inside the module. Callers can't set them. Use them to DRY up naming conventions and encode environment-specific logic:

locals.tflocals {
  # Single naming convention — defined once, used everywhere
  name_prefix = "empower-${var.environment}"

  # Merge caller tags with mandatory platform tags
  common_tags = merge(var.tags, {
    ManagedBy   = "Terraform"
    Environment = var.environment
    CostCenter  = "empower-pms"
  })

  # Conditional expression — ternary syntax
  key_vault_sku = var.environment == "prod" ? "premium" : "standard"

  # Lookup from a map — elegant env-based config
  aks_node_count = {
    dev     = 1
    staging = 2
    prod    = 3
  }[var.environment]
}

# Reference: local.name_prefix, local.common_tags, etc.
locals vs variables

If a caller should be able to override it → variable. If it's derived from other values and callers shouldn't control it → local. Naming conventions, tag merges, and conditional logic all belong in locals.

📤 Outputs: Exporting Values

Outputs serve two purposes: display values after apply, and expose values to parent modules that call this one.

outputs.tfoutput "resource_group_name" {
  value       = azurerm_resource_group.main.name
  description = "Name of the core resource group"
}

output "aks_cluster_id" {
  value       = azurerm_kubernetes_cluster.main.id
  description = "ARM resource ID of the AKS cluster"
}

output "key_vault_uri" {
  value       = azurerm_key_vault.main.vault_uri
  sensitive   = true   # redacted in terminal; still accessible in state
}

output "service_bus_connection" {
  value       = azurerm_servicebus_namespace.main.default_primary_connection_string
  sensitive   = true
}
reading outputs# Show all outputs
terraform output

# Plain text — pipe into scripts
terraform output -raw resource_group_name

# Reveal sensitive output
terraform output -raw key_vault_uri

# JSON — for CI pipelines and automation
terraform output -json
sensitive = true gotcha

Marking an output sensitive only redacts it from the terminal. The value is still stored in plaintext in the state file. Encrypt your state backend — do not mistake sensitive = true for actual encryption.
