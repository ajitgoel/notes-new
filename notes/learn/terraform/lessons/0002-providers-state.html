🔌 Providers: Terraform's Plugin Layer

Terraform itself knows no cloud APIs. Providers are plugins — downloaded by terraform init — that translate HCL into API calls. The Azure provider (azurerm) is maintained by Microsoft and HashiCorp jointly.

hashicorp/azurerm

The main Azure provider. Covers 700+ resource types: AKS, Key Vault, Service Bus, SQL, networking, and more.

hashicorp/azuread

Separate provider for Azure Active Directory resources: service principals, app registrations, group memberships.

hashicorp/random

Generates random values (strings, integers, UUIDs) for resource names that need uniqueness.

hashicorp/time

Time-based resources and functions. Useful for certificate expiry, key rotation triggers.

providers.tf — production patternterraform {
  required_version = ">= 1.6.0"
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 3.100"
    }
    azuread = {
      source  = "hashicorp/azuread"
      version = "~> 2.47"
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
  }
}

provider "azurerm" {
  features {
    key_vault {
      purge_soft_delete_on_destroy    = false   # keep soft-deleted vaults
      recover_soft_deleted_key_vaults = true
    }
    resource_group {
      prevent_deletion_if_contains_resources = true  # safety net
    }
  }
  subscription_id = var.subscription_id
}
Version Constraints

~> 3.100 means pessimistic constraint: >= 3.100 but < 4.0. This allows patch/minor updates but blocks major breaking changes. Always pin to a major version in production.

📦 What Is State?

State is a JSON file that maps your HCL configuration to real cloud resource IDs. Without it, Terraform can't know what it already created — it would try to create everything again on every apply.

The state file contains sensitive data — resource IDs, connection strings, passwords marked sensitive. Treat it like a secret store. It must live in remote storage, never in git.

☁️ Azure Blob Backend — The Right Setup

For Empower PMS (and any production system), state lives in Azure Blob Storage with locking via lease acquisition. Here's how to bootstrap it with a shell script you run once before terraform init:

bootstrap-state.sh#!/bin/bash
# Run this ONCE to create the state backend infrastructure
# This is the only Azure resource you create outside Terraform

RESOURCE_GROUP="rg-tfstate-prod"
LOCATION="westus2"
STORAGE_ACCOUNT="empowerpmsstate"    # must be globally unique
CONTAINER="tfstate"

az group create \
  --name $RESOURCE_GROUP \
  --location $LOCATION

az storage account create \
  --name $STORAGE_ACCOUNT \
  --resource-group $RESOURCE_GROUP \
  --location $LOCATION \
  --sku Standard_LRS \
  --kind StorageV2 \
  --min-tls-version TLS1_2 \
  --allow-blob-public-access false

az storage container create \
  --name $CONTAINER \
  --account-name $STORAGE_ACCOUNT

# Enable versioning — gives you state file history
az storage account blob-service-properties update \
  --account-name $STORAGE_ACCOUNT \
  --resource-group $RESOURCE_GROUP \
  --enable-versioning true
providers.tf — backend blockterraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate-prod"
    storage_account_name = "empowerpmsstate"
    container_name       = "tfstate"
    # key = environment + stack. One state file per workspace.
    key                  = "empower-pms/core.tfstate"
    use_azuread_auth     = true   # no storage account key needed
  }
}
use_azuread_auth = true

This uses your current AAD identity (service principal or managed identity) instead of storage account keys. Simpler rotation, better audit trail, fewer secrets to manage. Requires your identity to have Storage Blob Data Owner on the container.

🔐 Authentication: How Terraform Talks to Azure

Terraform reads credentials in this priority order:

authentication methods (highest to lowest priority)# 1. Environment variables (CI/CD pipelines)
ARM_CLIENT_ID="<service-principal-id>"
ARM_CLIENT_SECRET="<service-principal-secret>"
ARM_TENANT_ID="<tenant-id>"
ARM_SUBSCRIPTION_ID="<subscription-id>"

# 2. Azure CLI (local development — run: az login)
# Terraform picks up the active az cli session automatically.

# 3. Managed Identity (AKS workloads, Azure DevOps agents)
# No creds needed — identity is the compute resource.
Never hardcode credentials

Don't put client_secret in your provider block. Use environment variables or a Managed Identity. The provider block should only contain non-secret config like subscription_id.

🔒 State Locking

When two engineers run terraform apply simultaneously, state corruption can occur. The Azure backend uses blob lease acquisition as a distributed lock — the second apply will wait or fail until the first completes.

useful state commands# List all resources tracked in state
terraform state list

# Show detailed state for a specific resource
terraform state show azurerm_key_vault.main

# Move a resource (rename without destroying)
terraform state mv azurerm_resource_group.old azurerm_resource_group.new

# Remove from state without destroying the real resource
terraform state rm azurerm_resource_group.main

# Force unlock if a previous apply crashed (use with caution)
terraform force-unlock <lock-id>
