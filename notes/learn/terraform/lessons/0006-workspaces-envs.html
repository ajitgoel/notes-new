Workspaces &
Multi-Env Patterns

Two competing strategies for managing dev/staging/prod — Terraform workspaces vs directory-per-environment — and when each is right for Empower PMS.

⚖️ Two Strategies

The most common Terraform architecture question is: how do I manage multiple environments? There are two dominant approaches:

Terraform Workspaces
  • Single codebase, multiple state files
  • Fast to set up for simple cases
  • Built into Terraform core
  • Same config for all envs — hard to vary resources
  • Easy to accidentally apply to wrong env
  • Workspace name leaks into all resource naming logic
  • Not suited for major structural differences between envs
Directory Per Environment
  • Explicit separation — impossible to confuse envs
  • Prod can have completely different resources
  • Independent state files with clear paths
  • Industry standard for HIPAA / regulated systems
  • Some duplication in tfvars across envs
  • Slightly more initial setup
Recommendation for Empower PMS

Use directory-per-environment. For a HIPAA-regulated pharmacy system, the blast radius of an accidental prod apply must be minimized. Directories make environment boundaries explicit and auditable. Workspaces are fine for simple SaaS; not right here.

🗂️ Workspaces — How They Work

Even if you don't use workspaces as your primary strategy, you'll encounter them and the patterns are useful:

workspace commands# List workspaces (default = always exists)
terraform workspace list

# Create and switch to a new workspace
terraform workspace new staging

# Switch between existing workspaces
terraform workspace select prod

# Show current workspace
terraform workspace show

# Delete a workspace (must not be selected)
terraform workspace delete staging
using terraform.workspace in configlocals {
  # Workspace name becomes part of resource naming
  env = terraform.workspace

  # Map workspace to Azure region
  region = {
    default = "westus2"
    staging = "westus2"
    prod    = "westus2"  # could differ for DR
  }[terraform.workspace]

  # Different AKS node counts per workspace
  aks_nodes = {
    default = 1
    staging = 2
    prod    = 3
  }[terraform.workspace]
}

# State is stored at: tfstate/env:/staging/empower.tfstate

📁 Directory-Per-Env Pattern (Recommended)

Each environment is a fully independent root module. They share modules but have separate state, separate tfvars, and separate backends:

environments/prod/providers.tfterraform {
  required_version = ">= 1.6.0"
  required_providers {
    azurerm = { source = "hashicorp/azurerm"; version = "~> 3.100" }
  }

  backend "azurerm" {
    resource_group_name  = "rg-tfstate-global"
    storage_account_name = "empowerpmsstate"
    container_name       = "tfstate"
    key                  = "prod/core.tfstate"  # unique key per env
    use_azuread_auth     = true
  }
}

provider "azurerm" {
  features {}
  subscription_id = var.subscription_id
}
environments/prod/terraform.tfvarsenvironment      = "prod"
location         = "westus2"
subscription_id  = "<prod-subscription-id>"

aks_node_pool = {
  vm_size    = "Standard_D8s_v3"   # larger in prod
  node_count = 5
}

tags = {
  Environment = "prod"
  Compliance  = "HIPAA"
  CostCenter  = "pharmacy-ops"
}

🔒 Separate Subscriptions Per Environment

For serious compliance postures (HIPAA, SOC2), go one step further: separate Azure subscriptions per environment. This gives you hard blast-radius isolation — a prod credential compromise can't touch dev infra:

multi-subscription pattern# environments/prod — different subscription_id in tfvars
# environments/dev  — different subscription_id in tfvars
# Each subscription has its own RBAC, policies, budget alerts

# In Azure DevOps: separate service connections per subscription
# Pipeline variable groups:
# - empower-pms-dev-vars (dev subscription SPN)
# - empower-pms-prod-vars (prod subscription SPN with MFA/PIM)

🚀 CI/CD Pipeline Pattern

A typical Azure DevOps pipeline for Terraform in a regulated environment:

azure-pipelines.yml (simplified)stages:
  - stage: plan
    jobs:
      - job: terraform_plan
        steps:
          - script: |
              cd environments/$(TARGET_ENV)
              terraform init
              terraform plan -out=tfplan -var-file=terraform.tfvars
          - publish: tfplan       # save plan artifact

  - stage: apply
    dependsOn: plan
    # Requires manual approval for staging/prod
    jobs:
      - deployment: terraform_apply
        environment: $(TARGET_ENV)   # Azure DevOps approval gate
        steps:
          - download: current
          - script: |
              cd environments/$(TARGET_ENV)
              terraform init
              terraform apply -auto-approve tfplan
Plan → Approve → Apply

Always separate plan from apply in pipelines. The plan artifact ensures you apply exactly what was reviewed, not a potentially different plan generated at apply time. Azure DevOps Environments provide the approval gate.

🧠 Knowledge Check

Three questions on multi-environment strategy.

1. Why is directory-per-environment safer than workspaces for a HIPAA system?

A. Directories encrypt state automatically; workspaces don't
B. Separate directories with separate backends make it impossible to accidentally apply prod config — you must physically cd into the prod directory
C. Workspaces share the same state file; directories don't
D. Workspaces are deprecated in Terraform 1.6+

2. What is the key argument in the Azure backend block?

A. The storage account access key
B. The blob path within the container — the filename of the state file
C. An encryption key for the state
D. The Azure region key alias

3. In a CI/CD pipeline, why save the plan output as an artifact and apply it later, rather than running terraform plan && terraform apply in sequence?

A. Performance — it's faster to apply a saved plan
B. To guarantee the applied changes are exactly what was reviewed and approved — state can change between plan and apply if run separately
C. Terraform requires a plan file to run apply
D. The plan file contains provider credentials needed for apply
