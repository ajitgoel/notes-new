Subscription Filters: The Core Concept

Every subscription has rules. A rule is a filter (which messages to select) plus an optional action (how to modify them). The default rule on every new subscription is a TrueFilter — it selects everything.[source]

Filter Types

TypeHow it worksPerformanceUse when
SQL Filter SQL-like expression: Priority = 'High' AND Amount > 1000 ⚠️ Slower (requires parsing/eval) Complex conditions, arithmetic, LIKE, EXISTS
Correlation Filter Exact match on properties: Subject = 'order/created' ✅ Fast (hash lookup) Simple property matching — prefer this
TrueFilter / FalseFilter Select all / select none ✅ Fastest Broadcast (TrueFilter) or temporarily disabling a sub (FalseFilter)
⚠️ Performance note: SQL filters consume CPU on the broker. Under high throughput, prefer correlation filters. They use hash-based matching and have significantly less impact on throughput. SQL filters are powerful but expensive — use them when you genuinely need expressions, not just property matching.

Java: Creating Topics and Subscriptions Programmatically

TopicSetup.java
import com.azure.messaging.servicebus.administration.*;
import com.azure.messaging.servicebus.administration.models.*;
import java.time.Duration;

public class TopicSetup {

    private final ServiceBusAdministrationClient adminClient;

    public TopicSetup(String connectionString) {
        this.adminClient = new ServiceBusAdministrationClientBuilder()
            .connectionString(connectionString)
            .buildClient();
    }

    public void setup() {
        String topicName = "orders";

        // 1. Create the topic
        adminClient.createTopic(new CreateTopicOptions(topicName)
            .setMaxSizeInMegabytes(5120)
            .setDefaultMessageTimeToLive(Duration.ofDays(14))
            .setDuplicateDetectionHistoryTimeWindow(Duration.ofMinutes(10)));

        // 2. Subscription: all orders (audit trail)
        adminClient.createSubscription(
            new CreateSubscriptionOptions(topicName, "order-audit"));

        // 3. Subscription: high priority only (SQL filter)
        adminClient.createSubscription(topicName, "high-priority");
        adminClient.createRule(topicName, "high-priority",
            new CreateRuleOptions("high-prio-rule",
                new SqlRuleFilter("Priority = 'High'")));

        // 4. Subscription: large orders (SQL filter with compound condition)
        adminClient.createSubscription(topicName, "large-orders");
        adminClient.createRule(topicName, "large-orders",
            new CreateRuleOptions("large-orders-rule",
                new SqlRuleFilter("Amount > 5000 AND Region = 'eastus'")));

        // 5. Subscription: fulfillment for eastus (correlation filter — faster)
        adminClient.createSubscription(topicName, "fulfillment-eastus");
        adminClient.createRule(topicName, "fulfillment-eastus",
            new CreateRuleOptions("eastus-rule",
                new CreateRuleFilter()
                    .setSubject("order/created")
                    .addProperty("Region", "eastus")));

        // 6. Subscription with a FILTER ACTION: transform message
        adminClient.createSubscription(topicName, "discounted-orders");
        adminClient.createRule(topicName, "discounted-orders",
            new CreateRuleOptions("discount-rule",
                new SqlRuleFilter("HasDiscount = true"),
                new SqlRuleAction("SET Amount = Amount * 0.9; " +
                                  "SET DiscountedAt = sys.EnqueuedTimeUtc")));

        System.out.println("Topic + 6 subscriptions created.");
    }
}
Key detail: rules without actions combine via OR. If you create two rules without actions on a subscription and a message matches both, you get one copy on the subscription. Rules with actions each produce their own copy. So if a message matches 2 rules with actions and 3 without, you get 3 copies: 2 (one per action rule) + 1 (combined OR from the 3 non-action rules).

Sending to a Topic (Same API as Queues)

From the sender's perspective, sending to a topic is identical to sending to a queue. You don't know or care how many subscriptions exist.

TopicPublisher.java
import com.azure.messaging.servicebus.*;
import reactor.core.publisher.Mono;
import java.util.Map;

public class TopicPublisher {

    private final ServiceBusSenderAsyncClient sender;

    public TopicPublisher(String connectionString, String topicName) {
        this.sender = new ServiceBusClientBuilder()
            .connectionString(connectionString)
            .sender()
            .topicName(topicName)    // <-- topic, not queue
            .buildAsyncClient();
    }

    public Mono<Void> publishOrder(Order order) {
        ServiceBusMessage message = new ServiceBusMessage(order.toJson())
            .setMessageId(order.getId())
            .setContentType("application/json")
            .setSubject("order/created")         // used by correlation filters
            .setCorrelationId(order.getRegion()); // also used by correlation filters

        // Application properties — filterable by both SQL and correlation filters
        message.getApplicationProperties().putAll(Map.of(
            "Priority", order.isRush() ? "High" : "Normal",
            "Amount", order.getAmount(),
            "Region", order.getRegion(),
            "HasDiscount", order.hasDiscount()
        ));

        return sender.sendMessage(message);
    }

    public void close() { sender.close(); }
}

Receiving from a Subscription (Same API as Queues)

A subscription is consumed exactly like a queue. Multiple consumers on the same subscription compete for messages.

SubscriptionConsumer.java
import com.azure.messaging.servicebus.*;
import com.azure.messaging.servicebus.models.ServiceBusReceiveMode;

public class SubscriptionConsumer {

    private final ServiceBusProcessorClient processor;

    public SubscriptionConsumer(String connectionString,
                                String topicName,
                                String subscriptionName) {
        this.processor = new ServiceBusClientBuilder()
            .connectionString(connectionString)
            .processor()
            .topicName(topicName)              // <-- topic
            .subscriptionName(subscriptionName) // <-- subscription
            .receiveMode(ServiceBusReceiveMode.PEEK_LOCK)
            .maxConcurrentCalls(5)
            .autoComplete(false)
            .processMessage(ctx -> {
                System.out.printf("[%s] Received: %s%n",
                    subscriptionName,
                    ctx.getMessage().getBody().toString());
                ctx.complete();
            })
            .processError(ctx ->
                System.err.println("Error: " + ctx.getException().getMessage()))
            .buildProcessorClient();
    }

    public void start() { processor.start(); }
    public void close() { processor.close(); }
}

Pattern 1: Broadcast (TrueFilter)

Every subscription gets every message. This is the default — no custom rules needed.

Publisher ──► Topic ──► sub "audit" (all messages) ──► sub "analytics" (all messages) ──► sub "notification"(all messages) Use case: Multiple independent services all need to react to every order.

Pattern 2: Partitioning (Mutually Exclusive Filters)

Each subscription gets a non-overlapping subset. Used to scale out processing by shard key.

Topic "orders" │ ├── sub "region-eastus" (filter: Region = 'eastus') ├── sub "region-westus" (filter: Region = 'westus') └── sub "region-europe" (filter: Region = 'europe') Use case: Each region has its own fulfillment service. Each message goes to exactly ONE subscription.

Pattern 3: Content-Based Routing (Overlapping Filters)

Messages route to different services based on their content. Some messages may go to multiple subscriptions.

Order #1: Priority=High, Amount=2000, Region=eastus │ ├── sub "high-priority" ✅ (Priority = High) ├── sub "large-orders" ❌ (Amount < 5000) └── sub "audit" ✅ (all messages) Order #2: Priority=Normal, Amount=7500, Region=eastus │ ├── sub "high-priority" ❌ ├── sub "large-orders" ✅ (Amount > 5000 AND Region = eastus) └── sub "audit" ✅ (all messages)

Pattern 4: Filter Actions — Transform in Flight

Filter actions modify message application properties before they land in the subscription. The original message on the topic is unchanged — only the subscription's copy is modified.

// Example: Apply a regional discount before consumers see the message
CreateRuleOptions discountRule = new CreateRuleOptions("eastus-discount",
    new SqlRuleFilter("Region = 'eastus'"),
    new SqlRuleAction(
        "SET Amount = Amount * 0.85; " +
        "SET AppliedDiscount = '15%'; " +
        "SET DiscountedBy = 'region-promo'"
    ));

adminClient.createRule("orders", "fulfillment-eastus", discountRule);

// The consumer reading from "fulfillment-eastus" sees Amount at 85%
// Consumers reading from other subscriptions see the original Amount
⚠️ Actions cannot modify the message body or system properties. You can SET, REMOVE, or update application properties only. Changing system properties like MessageId or SessionId can break deduplication and session routing.

Key Takeaways

  • Topics send copies, not references. Each matching subscription gets its own independent copy of the message, with its own lock, delivery count, and DLQ.
  • Prefer correlation filters over SQL filters. They're faster (hash match vs. expression eval) and have less throughput impact. Use SQL only when you need arithmetic, LIKE, or compound conditions.
  • Rules with actions produce separate copies. Rules without actions combine via OR. Plan your rule count — each rule with an action adds broker CPU overhead.
  • Sending to a topic is identical to sending to a queue. Receiving from a subscription is identical to receiving from a queue. The only difference is in entity setup.
  • Each subscription has its own DLQ. A message can succeed on one subscription and dead-letter on another — they're independent.
