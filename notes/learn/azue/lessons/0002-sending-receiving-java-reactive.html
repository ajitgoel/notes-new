Core Clients

The modern SDK provides two parallel client hierarchies — one synchronous (blocking), one asynchronous (reactive).[API Reference]

Role Sync (blocking) Async (reactive — use these)
Entry point / connection ServiceBusClientBuilder → builds async clients
Send messages ServiceBusSenderClient ServiceBusSenderAsyncClient
Receive messages (manual) ServiceBusReceiverClient ServiceBusReceiverAsyncClient
Receive messages (push/callback) ServiceBusProcessorClient (event-driven, subscription-based)

Sending Messages (Reactive)

Create an async sender and send messages using Mono. The sender is lightweight — but the underlying AMQP connection is established lazily on first operation.

SendService.java
import com.azure.messaging.servicebus.*;
import reactor.core.publisher.Mono;

public class SendService {

    private final ServiceBusSenderAsyncClient senderClient;

    public SendService(String connectionString, String queueName) {
        this.senderClient = new ServiceBusClientBuilder()
            .connectionString(connectionString)
            .sender()
            .queueName(queueName)
            .buildAsyncClient();
    }

    public Mono<Void> sendOrder(Order order) {
        ServiceBusMessage message = new ServiceBusMessage(order.toJson())
            .setMessageId(order.getId())          // for duplicate detection
            .setContentType("application/json")
            .setSubject("order/created")          // useful for routing/filtering
            .setCorrelationId(order.getCustomerId());

        return senderClient.sendMessage(message);
        // Returns Mono<Void> — completes when broker acknowledges the message
    }

    public Mono<Void> sendBatch(Flux<Order> orders) {
        return orders
            .map(order -> new ServiceBusMessage(order.toJson())
                .setMessageId(order.getId())
                .setContentType("application/json"))
            .collectList()
            .flatMap(messages -> senderClient.sendMessages(messages));
    }

    public void close() {
        senderClient.close();
    }
}
🧭 Key API Insight

sendMessage() returns Mono<Void> — it doesn't complete until the broker acknowledges the message. This is settled send: you know the message was accepted. The Mono errors if the broker rejects it (throttling, auth failure, etc.). Never fire-and-forget a send — subscribe to the Mono or return it in your reactive chain.

Receiving Messages: PeekLock (The Default)

PeekLock is the default and recommended receive mode. It's a two-phase operation:[source]

  1. Receive + Lock — the broker locks the message (default 60s) and returns it. No other consumer can see it.
  2. Settle — you call complete(), abandon(), or deadLetter().
ReceiveService.java
import com.azure.messaging.servicebus.*;
import com.azure.messaging.servicebus.models.ServiceBusReceiveMode;
import reactor.core.publisher.Mono;
import java.time.Duration;

public class ReceiveService {

    private final ServiceBusReceiverAsyncClient receiverClient;

    public ReceiveService(String connectionString, String queueName) {
        this.receiverClient = new ServiceBusClientBuilder()
            .connectionString(connectionString)
            .receiver()
            .queueName(queueName)
            .receiveMode(ServiceBusReceiveMode.PEEK_LOCK)  // default, explicit for clarity
            .buildAsyncClient();
    }

    // Receive a single message with settlement
    public Mono<String> processNextMessage() {
        return receiverClient.receiveMessage()
            .flatMap(message -> {
                String body = message.getBody().toString();

                try {
                    // --- Your business logic here ---
                    processOrder(body);

                    // Success → complete (remove from queue)
                    return receiverClient.complete(message)
                        .thenReturn("Processed: " + message.getMessageId());

                } catch (TransientException e) {
                    // Temporary failure → abandon (unlock, make available again)
                    return receiverClient.abandon(message)
                        .thenReturn("Abandoned (will retry): " + message.getMessageId());

                } catch (FatalException e) {
                    // Permanent failure → dead-letter (move to DLQ)
                    return receiverClient.deadLetter(message,
                        new DeadLetterOptions()
                            .setDeadLetterReason("Fatal processing error")
                            .setDeadLetterErrorDescription(e.getMessage()))
                        .thenReturn("Dead-lettered: " + message.getMessageId());
                }
            });
    }

    // Continuous receive using Flux
    public Flux<String> processContinuously() {
        return Flux.interval(Duration.ofSeconds(1))
            .flatMap(i -> receiverClient.receiveMessage())
            .flatMap(message -> {
                String body = message.getBody().toString();
                processOrder(body);
                return receiverClient.complete(message)
                    .thenReturn("Processed: " + message.getMessageId());
            });
    }

    public void close() {
        receiverClient.close();
    }
}

Receiving Messages: ReceiveAndDelete (At-Most-Once)

For low-value messages where occasional loss is tolerable. The message is deleted as soon as the broker hands it to the client. No settlement needed — faster, fewer round trips.

FireAndForgetReceiver.java
ServiceBusReceiverAsyncClient receiver = new ServiceBusClientBuilder()
    .connectionString(connectionString)
    .receiver()
    .queueName("telemetry-queue")
    .receiveMode(ServiceBusReceiveMode.RECEIVE_AND_DELETE)  // at-most-once
    .buildAsyncClient();

// Messages are deleted immediately when received — no complete/abandon needed
receiver.receiveMessage()
    .flatMap(message -> {
        ingestTelemetry(message.getBody().toString());
        return Mono.empty();  // nothing to settle
    })
    .subscribe();

The ServiceBusProcessorClient: Push-Based Processing

For reactive applications, the ServiceBusProcessorClient is often the best choice. It's event-driven — messages are pushed to your handler via callbacks. You configure it to run with a thread pool for concurrent processing.

ProcessorService.java
import com.azure.messaging.servicebus.*;
import com.azure.messaging.servicebus.models.ServiceBusReceiveMode;
import reactor.core.publisher.Mono;

public class ProcessorService {

    private final ServiceBusProcessorClient processorClient;

    public ProcessorService(String connectionString, String queueName) {
        processorClient = new ServiceBusClientBuilder()
            .connectionString(connectionString)
            .processor()
            .queueName(queueName)
            .receiveMode(ServiceBusReceiveMode.PEEK_LOCK)
            .maxConcurrentCalls(10)             // process up to 10 concurrently
            .autoComplete(false)                 // we want manual settlement
            .processMessage(ctx -> handleMessage(ctx))
            .processError(ctx -> handleError(ctx))
            .buildProcessorClient();
    }

    private void handleMessage(ServiceBusReceivedMessageContext ctx) {
        ServiceBusReceivedMessage message = ctx.getMessage();
        String body = message.getBody().toString();

        try {
            processOrder(body);
            ctx.complete();      // settle: remove from queue
        } catch (TransientException e) {
            ctx.abandon();       // settle: unlock for retry
        } catch (FatalException e) {
            ctx.deadLetter(      // settle: move to DLQ
                new DeadLetterOptions()
                    .setDeadLetterReason("Fatal: " + e.getMessage()));
        }
    }

    private void handleError(ServiceBusErrorContext ctx) {
        // Called on transient errors (network blips, lock lost, etc.)
        // The processor auto-retries — logging is usually sufficient here
        log.error("Error processing: {}", ctx.getException().getMessage());
    }

    public void start() {
        processorClient.start();  // non-blocking — starts background threads
    }

    public void close() {
        processorClient.close();
    }
}
⚠️ Processor is NOT fully reactive

The ServiceBusProcessorClient uses callbacks and a thread pool — it's event-driven but not built on Project Reactor internally. For a fully reactive pipeline, use ServiceBusReceiverAsyncClient with manual receive + Flux. The processor is simpler for most use cases and performs well under load.

ServiceBusConfig.java
import com.azure.messaging.servicebus.*;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class ServiceBusConfig {

    @Value("${spring.cloud.azure.servicebus.connection-string}")
    private String connectionString;

    @Bean(destroyMethod = "close")
    public ServiceBusSenderAsyncClient orderSender() {
        return new ServiceBusClientBuilder()
            .connectionString(connectionString)
            .sender()
            .queueName("orders")
            .buildAsyncClient();
    }

    @Bean(destroyMethod = "close")
    public ServiceBusProcessorClient orderProcessor() {
        return new ServiceBusClientBuilder()
            .connectionString(connectionString)
            .processor()
            .queueName("orders")
            .receiveMode(ServiceBusReceiveMode.PEEK_LOCK)
            .maxConcurrentCalls(10)
            .autoComplete(false)
            .processMessage(ctx -> { /* handle */ })
            .processError(ctx -> { /* log */ })
            .buildProcessorClient();
    }
}
OrderController.java
import com.azure.messaging.servicebus.ServiceBusMessage;
import com.azure.messaging.servicebus.ServiceBusSenderAsyncClient;
import org.springframework.web.bind.annotation.*;
import reactor.core.publisher.Mono;

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final ServiceBusSenderAsyncClient sender;

    public OrderController(ServiceBusSenderAsyncClient sender) {
        this.sender = sender;
    }

    @PostMapping
    public Mono<Void> createOrder(@RequestBody Order order) {
        ServiceBusMessage message = new ServiceBusMessage(order.toJson())
            .setMessageId(order.getId())
            .setSubject("order/created");
        return sender.sendMessage(message);
    }
}

Key Takeaways

  • Use PeekLock by default. It gives you at-least-once delivery with the full settlement lifecycle.
  • Never fire-and-forget a send. The Mono<Void> from sendMessage() is your signal that the broker accepted the message. Return it or subscribe with error handling.
  • Settlement is explicit. Until you call complete(), abandon(), or deadLetter(), the message stays locked and invisible. When the lock expires, it reappears.
  • ServiceBusProcessorClient is the pragmatic choice for most consumers. It handles concurrency and retries. Only drop to ServiceBusReceiverAsyncClient when you need full reactive backpressure.
  • Clients are singletons. Create them once, reuse across your application. The AMQP connection is expensive — don't create a new client per message.
