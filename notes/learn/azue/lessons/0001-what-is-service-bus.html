Lesson 1: What Is Azure Service Bus?

Estimated time: 15–20 minutes  |  Focus: Concepts & Positioning

🎯 What you'll learn
By the end of this lesson, you'll be able to explain where Service Bus sits in the Azure messaging landscape and choose between it and other Azure messaging services for a given scenario. You'll understand the core entities and Service Bus's "superpowers" that differentiate it from RabbitMQ, Kafka, and SQS.

The 30-Second Definition

Azure Service Bus is a fully managed, serverless enterprise message broker. It provides:

  1. Message queues — point-to-point, competing consumers, FIFO
  2. Publish-subscribe topics — one-to-many with per-subscriber filtering
  3. Enterprise-grade guarantees — transactions, duplicate detection, sessions, dead-lettering

If you've used RabbitMQ: Service Bus is like a fully-managed RabbitMQ cluster where you never touch a server. If you've used SQS: it's SQS plus topics, transactions, automatic dead-lettering, and FIFO without the throughput limits.

Where It Fits: The Azure Messaging Trinity

Azure has three messaging services. They're complementary — many systems use all three. The distinction hinges on one question: events or messages?[source]

🧭 Quick Heuristic

Is the consumer expected to act on and acknowledge each item? → Service Bus
Is the data a firehose of telemetry for analysis? → Event Hubs
Are you wiring Azure services together reactively? → Event Grid

Core Entities: Queues vs. Topics

📬 Queues

A queue is a point-to-point channel. Each message is consumed by exactly one receiver. Multiple receivers compete for messages — this is the competing consumers pattern you know from RabbitMQ and SQS.

Key characteristics:

  • FIFO ordering (timestamped on arrival)
  • Durable storage in triple-redundant storage
  • Pull-based with long-polling (not busy-polling)
  • Supports sessions for strict FIFO within a group

Use when: distributing work across workers, load leveling, temporal decoupling.

📢 Topics & Subscriptions

A topic enables one-to-many publish-subscribe. Each subscription acts like a virtual queue — it gets a copy of every message (subject to filters). Subscribers compete for messages within a subscription independently from other subscriptions.

Key superpower — Subscription Filters:

  • SQL filters — e.g., Priority = 'High' AND Region = 'eastus'
  • Correlation filters — match on specific property values (more efficient)
  • Filter actions — modify message properties as they pass through the subscription (e.g., add a RoutedAt timestamp)

Use when: multiple services need to react to the same event, fan-out, event-driven microservices.

🧭 Rule of Thumb

If your system is production, needs predictable latency, or requires VNet isolation → Premium. If you're prototyping or throughput is modest and variable → Standard.

Key Takeaway

Service Bus is the "enterprise message broker" of Azure. It's the service you reach for when each message matters — when you need to know whether a message was processed, retry it if not, move it to a dead-letter queue if it's poison, and do it all within atomic transactions.
