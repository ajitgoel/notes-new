Lesson 5: Message Sessions — Ordered Processing & Workflows

Estimated time: 20–25 minutes  |  Focus: FIFO, Session State, Request-Response

🎯 What you'll learn
How to use message sessions to guarantee FIFO processing within related message groups, manage session state for workflow recovery, implement the request-response pattern, and use the Java session processor API.

The Problem Sessions Solve

Standard queues guarantee FIFO ordering but not FIFO processing. With multiple consumers, messages 1, 2, 3 can be processed in any order depending on which consumer is fastest. Sessions enforce that all messages with the same SessionId are processed sequentially by the same consumer.[source]

WITHOUT SESSIONS: WITH SESSIONS: Queue: [1A, 1B, 2A, 1C, 2B] Queue: [1A, 1B, 2A, 1C, 2B] │ │ Consumer 1 gets 1A Session "1" ──► Consumer A Consumer 2 gets 1B ← WRONG! Session "2" ──► Consumer B Consumer 1 gets 2A │ │ Consumer 2 gets 1C ← WRONG! 1A → 1B → 1C (strict order) Consumer 1 gets 2B 2A → 2B (strict order) Result: 1A, 2A processed Each session is a virtual before 1B, 1C — order broken sub-queue with its own lock

How Sessions Work

  1. Enable sessions on the queue or subscription at creation time (cannot be changed later).
  2. Senders set SessionId on messages. All messages with the same SessionId form a session.
  3. A consumer accepts a session — it gets an exclusive lock on that session ID across all messages (past and future).
  4. Messages within the session are delivered FIFO. Only one consumer holds the session lock.
  5. When the consumer closes the session or the lock expires, another consumer can accept it.
⚠️ When sessions are enabled, ALL messages MUST have a SessionId. You can't send regular non-session messages to a session-enabled queue. This is a hard requirement — the send will fail if SessionId is null.

Java API: Session Sender

SessionSender.java
import com.azure.messaging.servicebus.*;
import reactor.core.publisher.Mono;

public class SessionSender {

    private final ServiceBusSenderAsyncClient sender;

    public SessionSender(String connectionString, String queueName) {
        this.sender = new ServiceBusClientBuilder()
            .connectionString(connectionString)
            .sender()
            .queueName(queueName)
            .buildAsyncClient();
    }

    // All messages for the same order share a SessionId
    public Mono<Void> sendOrderWorkflow(String orderId, String step, String payload) {
        return sender.sendMessage(new ServiceBusMessage(payload)
            .setMessageId(orderId + "-" + step)
            .setSessionId(orderId)          // <-- ties messages together
            .setSubject("order/" + step)    // e.g., "order/created", "order/paid"
            .setContentType("application/json"));
    }
}

Java API: Session Receiver (Accept Any Session)

SessionReceiver.java
import com.azure.messaging.servicebus.*;
import com.azure.messaging.servicebus.models.ServiceBusReceiveMode;
import reactor.core.publisher.Mono;

public class SessionReceiver {

    private final ServiceBusClientBuilder builder;

    public SessionReceiver(String connectionString) {
        this.builder = new ServiceBusClientBuilder()
            .connectionString(connectionString);
    }

    // Accept the next available session (any SessionId)
    public Mono<Void> processNextSession(String queueName) {
        ServiceBusSessionReceiverAsyncClient sessionReceiver = builder
            .sessionReceiver()                       // <-- session receiver
            .queueName(queueName)
            .receiveMode(ServiceBusReceiveMode.PEEK_LOCK)
            .buildAsyncClient();

        return sessionReceiver.receiveMessages()
            .flatMap(message -> {
                System.out.printf("[Session: %s] %s: %s%n",
                    message.getSessionId(),
                    message.getSubject(),
                    message.getBody().toString());

                // Process in order — guaranteed within this session
                return processBusinessLogic(message)
                    .then(sessionReceiver.complete(message));
            })
            .then(Mono.fromRunnable(sessionReceiver::close));
    }
}

Java API: Session Processor (Production-Ready)

The ServiceBusSessionProcessorClient manages multiple sessions concurrently — it auto-accepts available sessions and distributes them across a thread pool.[sample]

SessionProcessorService.java
import com.azure.messaging.servicebus.*;
import com.azure.messaging.servicebus.models.*;

public class SessionProcessorService {

    private final ServiceBusSessionProcessorClient processor;

    public SessionProcessorService(String connectionString, String queueName) {
        processor = new ServiceBusClientBuilder()
            .connectionString(connectionString)
            .sessionProcessor()                           // <-- session processor
            .queueName(queueName)
            .maxConcurrentSessions(5)                     // process 5 sessions in parallel
            .maxConcurrentCalls(2)                        // max 2 concurrent msgs per session
            .receiveMode(ServiceBusReceiveMode.PEEK_LOCK)
            .autoComplete(false)
            .processMessage(ctx -> handleSessionMessage(ctx))
            .processError(ctx -> log.error("Error: {}",
                ctx.getException().getMessage()))
            .buildSessionProcessorClient();
    }

    private void handleSessionMessage(ServiceBusSessionReceiverMessageContext ctx) {
        ServiceBusReceivedMessage msg = ctx.getMessage();

        try {
            // Session state: checkpoint where we are in the workflow
            byte[] currentState = ctx.getSessionReceiver().getSessionState();
            String lastStep = currentState != null
                ? new String(currentState) : "none";

            log.info("[Session: {}] Processing {} (last completed: {})",
                msg.getSessionId(), msg.getSubject(), lastStep);

            processStep(msg);

            // Save session state for recovery
            ctx.getSessionReceiver().setSessionState(
                msg.getSubject().getBytes());

            ctx.complete();

        } catch (FatalException e) {
            ctx.deadLetter(new DeadLetterOptions()
                .setDeadLetterReason("SessionFatal:" + e.getMessage()));
        } catch (Exception e) {
            ctx.abandon();  // transient — retry within session
        }
    }

    public void start() { processor.start(); }
    public void close() { processor.close(); }
}

Session State: The Recovery Superpower

Session state is an opaque binary blob stored on the broker (256 KB Standard, 100 MB Premium). It persists even after all messages in the session are consumed. Use it to checkpoint workflow progress.[source]

Session "order-12345" ┌────────────────────────────────────────────────┐ │ Messages: [created] → [payment-cleared] → [shipped] │ SessionState: "step=payment-cleared" └────────────────────────────────────────────────┘ If consumer crashes after processing "payment-cleared" but before "shipped", the NEW consumer reads session state and knows to skip to "shipped" — no duplicate processing.

Pattern: Request-Response with Sessions

Sessions enable request-response without creating temporary reply queues. The requester uses a unique SessionId (a GUID) and waits on a session receiver for the reply.[source]

RequestResponseService.java
import com.azure.messaging.servicebus.*;
import reactor.core.publisher.Mono;
import java.util.UUID;
import java.time.Duration;

public class RequestResponseService {

    private final ServiceBusSenderAsyncClient requestSender;
    private final ServiceBusClientBuilder builder;
    private static final String REQUEST_QUEUE = "requests";
    private static final String RESPONSE_QUEUE = "responses"; // session-enabled

    public RequestResponseService(String connectionString) {
        this.requestSender = new ServiceBusClientBuilder()
            .connectionString(connectionString)
            .sender().queueName(REQUEST_QUEUE).buildAsyncClient();
        this.builder = new ServiceBusClientBuilder()
            .connectionString(connectionString);
    }

    // --- REQUESTER sends request and waits for reply ---
    public Mono<String> sendRequestAndWaitForReply(String requestBody) {
        String correlationId = UUID.randomUUID().toString();

        // Send request with a ReplyToSessionId the responder will use
        return requestSender.sendMessage(new ServiceBusMessage(requestBody)
            .setMessageId(correlationId)
            .setReplyToSessionId(correlationId)  // responder sets this as SessionId on reply
            .setReplyTo(RESPONSE_QUEUE))
            .then(receiveReply(RESPONSE_QUEUE, correlationId));
    }

    private Mono<String> receiveReply(String queueName, String sessionId) {
        ServiceBusSessionReceiverAsyncClient sessionReceiver = builder
            .sessionReceiver()
            .queueName(queueName)
            .sessionId(sessionId)          // wait for THIS specific session
            .buildAsyncClient();

        return sessionReceiver.receiveMessage()
            .flatMap(msg ->
                sessionReceiver.complete(msg)
                    .thenReturn(msg.getBody().toString()))
            .timeout(Duration.ofSeconds(30))
            .doFinally(sig -> sessionReceiver.close());
    }

    // --- RESPONDER: processes request, sends reply ---
    public void startResponder() {
        ServiceBusSessionProcessorClient processor = builder
            .sessionProcessor()
            .queueName(REQUEST_QUEUE)
            .maxConcurrentSessions(10)
            .processMessage(ctx -> {
                ServiceBusReceivedMessage request = ctx.getMessage();
                String reply = processRequest(request.getBody().toString());

                // Send reply using the request's ReplyToSessionId as the SessionId
                ServiceBusSenderAsyncClient replySender = builder
                    .sender().queueName(request.getReplyTo()).buildAsyncClient();

                replySender.sendMessage(new ServiceBusMessage(reply)
                    .setSessionId(request.getReplyToSessionId())
                    .setCorrelationId(request.getMessageId()))
                    .block();  // fire-and-block in this callback context

                ctx.complete();
                replySender.close();
            })
            .processError(ctx -> log.error("Error", ctx.getException()))
            .buildSessionProcessorClient();
        processor.start();
    }
}

Session vs. Non-Session: When to Use Which

SessionsNo Sessions
Message orderingFIFO within sessionFIFO enqueue order, any process order
ConcurrencyOne consumer per session; many sessions in parallelMany consumers compete freely
State storageBroker-side session stateMust use external store
ThrougputLower per-session (serial), higher overall (many sessions)Highest (no session overhead)
Use whenOrdered workflows, state machines, request-replyIndependent tasks, load leveling, fire-and-forget
🧭 Pro tip: Sessions impose CPU overhead on the broker. If you have a high-throughput scenario (1,000s msg/sec), consider whether you genuinely need sessions. Often, designing messages to be independently processable (each message is self-contained, doesn't depend on order) is simpler and faster.

Key Takeaways

  • Sessions = FIFO processing, not just FIFO ordering. Without sessions, messages are in order in the queue but may be processed out of order by competing consumers.
  • Session lock is exclusive. Only one consumer processes a given SessionId at a time. This is the mechanism that guarantees ordering.
  • Session state survives message consumption. Use it for workflow checkpoints — but remember to clear it when the workflow is complete.
  • SessionProcessor is the production choice. Use maxConcurrentSessions to control parallelism across sessions while maintaining per-session ordering.
  • Request-response via sessions avoids temporary queues. The requester creates a unique SessionId and waits on a session receiver; the responder sets that as the reply's SessionId.
