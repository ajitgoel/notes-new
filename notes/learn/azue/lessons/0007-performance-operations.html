Part 1: Throughput Tuning

Prefetch: The Biggest Lever

Prefetch downloads messages into a local cache before your code asks for them, dramatically reducing round trips. Default is 0 (disabled).[source]

SettingGuidelineTradeoff
prefetchCount = 0 Default — no prefetch Lowest latency per-message, more round trips
prefetchCount = 20 × processing_rate High throughput (recommended starting point) Higher throughput, messages locked in cache until processed
prefetchCount too high Messages expire in cache while locked Wasted locks, redelivery, confused consumers 
// Configure prefetch on receiver
ServiceBusReceiverAsyncClient receiver = new ServiceBusClientBuilder()
    .connectionString(connectionString)
    .receiver()
    .queueName("orders")
    .prefetchCount(200)               // cache 200 messages locally
    .receiveMode(ServiceBusReceiveMode.PEEK_LOCK)
    .buildAsyncClient();

// Or on processor
ServiceBusProcessorClient processor = new ServiceBusClientBuilder()
    .connectionString(connectionString)
    .processor()
    .queueName("orders")
    .prefetchCount(200)
    .maxConcurrentCalls(20)
    .buildProcessorClient();

Concurrent Operations & Client Reuse

  1. Reuse clients. Create ServiceBusSenderAsyncClient and ServiceBusProcessorClient as Spring singletons. The AMQP connection is expensive — don't create per-message.
  2. Send asynchronously and concurrently. Don't await each send sequentially. Fire multiple sends and await them together with Mono.when().
  3. Use maxConcurrentCalls on the processor to control parallel message processing. Default is 1 — increase for higher throughput.
  4. AMQP is faster than HTTP. The SDK uses AMQP by default. Never use HTTP for production throughput.
// BAD: sequential sends
for (Order order : orders) {
    sender.sendMessage(toMessage(order)).block(); // blocks N times
}

// GOOD: concurrent sends
List<Mono<Void>> sends = orders.stream()
    .map(o -> sender.sendMessage(toMessage(o)))
    .collect(Collectors.toList());
Mono.when(sends).block();    // all sent concurrently

Partitioning: Scale Through Parallelism

Partitioning splits a queue or topic across multiple brokers internally. In Standard tier, partitioning creates 16 partitions. In Premium, you specify the partition count at namespace creation.[source]

Non-PartitionedPartitioned
ThroughputLimited to single brokerScales linearly with partitions
OrderingFIFO within queueFIFO within partition only
Duplicate detectionMessageId onlyMessageId + PartitionKey
SessionsSingle brokerSessionId = PartitionKey
Use whenSimple, low-medium throughputHigh throughput (>1,000 msg/sec)

Part 2: Messaging Unit Capacity Planning (Premium)

Each Messaging Unit (MU) provides approximately ~4 MB/s combined ingress + egress. Monitor CPU usage to decide when to scale.[source]

CPU metricAction
< 20%Consider scaling DOWN (reduce MUs to save cost)
20–70%Healthy range — no action needed
> 70%Scale UP (add MUs to avoid throttling)

Features that consume CPU and reduce throughput:

  • Sessions
  • Fan-out to many subscriptions on a single topic
  • SQL filters (especially many per subscription)
  • Scheduled messages, deferred messages, transactions
  • Duplicate detection
# Auto-scale messaging units (via Azure Monitor alert + Logic App/Automation)
# Or manual scaling:
az servicebus namespace update \
  --resource-group myrg \
  --name mysb \
  --capacity 4           # 4 messaging units

  --metric "ActiveMessages" "DeadletteredMessages" \
  --interval PT1M

# Create an alert on DLQ count
az monitor metrics alert create \
  --name "DLQ-Not-Empty" \
  --resource /subscriptions/.../namespaces/mysb/queues/orders \
  --condition "avg DeadletteredMessages > 0" \
  --window-size 5m \
  --evaluation-frequency 1m \
  --action /subscriptions/.../actionGroups/oncall

Part 4: Geo-Replication & Disaster Recovery

Geo-replication continuously replicates metadata AND data from a primary namespace to one or more secondary regions. Promoting a secondary is nearly instantaneous.[source]

What gets replicated:
  • ✅ Queues, topics, subscriptions, filters
  • ✅ Message data (both active and dead-lettered)
  • ✅ Message state changes (locks, settlements)
  • ✅ Namespace configuration
  • ❌ SAS keys / RBAC assignments (these are regional)
# Create geo-replication pairing (Premium only)
az servicebus namespace geo-replication-configuration set \
  --resource-group myrg \
  --namespace-name mysb-primary \
  --alias myalias \
  --partner-namespace /subscriptions/.../namespaces/mysb-secondary

# In a disaster: promote secondary to primary
az servicebus namespace geo-replication-configuration break-pairing \
  --resource-group myrg \
  --namespace-name mysb-secondary

# Your clients should use the alias, not the namespace directly
# Connection string: sb://myalias.servicebus.windows.net/

Key Takeaways

  • Prefetch is your biggest throughput lever. Start at 20× processing rate. Don't exceed (lock_duration / processing_time) or you'll get lock expiry and duplicates.
  • CPU > 70% → scale up MUs. This is the primary signal. Auto-scale can be configured via Azure Monitor.
  • Reuse clients. One ServiceBusClient per namespace, one sender/receiver per entity. Spring singletons.
  • Monitor DLQ count, throttled requests, and server errors. These are leading indicators of problems.
  • Geo-replication replicates data too. Unlike the old Geo-DR (metadata only), the modern geo-replication preserves your messages across regions.
  • Partition for extreme scale. But be aware of ordering tradeoffs and partition key requirements for dedup/sessions.
