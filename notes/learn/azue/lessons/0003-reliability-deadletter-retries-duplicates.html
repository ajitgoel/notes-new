Part 1: The Dead-Letter Queue (DLQ)

Every Service Bus queue and topic subscription has a built-in dead-letter subqueue. It doesn't need to be created and can't be deleted — it just exists. Its purpose: hold messages that can't be delivered or processed.[source]

┌─────────────── Queue "orders" ───────────────┐ │ │ │ Active messages ──► Consumer │ │ │ │ │ │ │ complete │ abandon │ │ │ (delete) │ (retry later) │ │ │ │ │ │ └──── deadLetter ─────┘ │ │ ▼ │ │ ┌─── $deadletterqueue ───────────────────┐ │ │ │ │ │ │ │ Messages that: │ │ │ │ • Exceeded MaxDeliveryCount (default 10)│ │ │ │ • Expired (TTL passed) │ │ │ │ • Were explicitly dead-lettered │ │ │ │ • Failed subscription filter eval │ │ │ │ │ │ │ └────────────────────────────────────────┘ │ └───────────────────────────────────────────────┘

How Messages End Up in the DLQ

PathDeadLetterReasonWhen
MaxDeliveryCountExceeded System-set Message was abandoned or lock expired more than MaxDeliveryCount times (default 10). This is the most common path.
TTLExpiredException System-set Message's TimeToLive expired before it could be consumed. Only if dead-lettering on expiry is enabled.
Explicit deadLetter() Application-set Your code calls deadLetter() with a custom reason. This is for poison messages that will never succeed.
HeaderSizeExceeded System-set Message metadata exceeds size limits (rare).
MaxTransferHopCountExceeded System-set Message forwarded through more than 4 entities (autoforwarding chains).

DLQ Path

The DLQ is accessed via a well-known suffix:

// Queue DLQ
<queueName>/$deadletterqueue

// Subscription DLQ
<topicName>/Subscriptions/<subscriptionName>/$deadletterqueue

Accessing and Resubmitting DLQ Messages — Java Code

DeadLetterService.java
import com.azure.messaging.servicebus.*;
import com.azure.messaging.servicebus.models.*;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

public class DeadLetterService {

    private final ServiceBusClientBuilder builder;

    public DeadLetterService(String connectionString) {
        this.builder = new ServiceBusClientBuilder()
            .connectionString(connectionString);
    }

    // --- Read from DLQ ---
    public Flux<ServiceBusReceivedMessage> peekDeadLetters(String queueName) {
        ServiceBusReceiverAsyncClient dlqReceiver = builder
            .receiver()
            .queueName(queueName)
            .subQueue(SubQueue.DEAD_LETTER)     // key: targets the DLQ
            .receiveMode(ServiceBusReceiveMode.PEEK_LOCK)
            .buildAsyncClient();

        return Flux.using(
            () -> dlqReceiver,
            receiver -> receiver.receiveMessages()
                .flatMap(m -> Mono.just(m)),
            ServiceBusReceiverAsyncClient::close
        );
    }

    // --- Resubmit a dead-lettered message ---
    public Mono<Void> resubmit(String queueName, ServiceBusReceivedMessage dlqMessage) {
        ServiceBusReceiverAsyncClient dlqReceiver = builder
            .receiver()
            .queueName(queueName)
            .subQueue(SubQueue.DEAD_LETTER)
            .buildAsyncClient();

        ServiceBusSenderAsyncClient sender = builder
            .sender()
            .queueName(queueName)
            .buildAsyncClient();

        // Create a new message from the DLQ message's body
        ServiceBusMessage resubmitMsg = new ServiceBusMessage(dlqMessage.getBody())
            .setMessageId(dlqMessage.getMessageId())
            .setContentType(dlqMessage.getContentType());

        return sender.sendMessage(resubmitMsg)
            .then(dlqReceiver.complete(dlqMessage))   // remove from DLQ
            .doFinally(sig -> {
                dlqReceiver.close();
                sender.close();
            });
    }
}
⚠️ DLQ messages don't expire and won't be auto-cleaned. They stay until you explicitly complete them. Without monitoring, your DLQ can grow indefinitely. Set up alerts on DLQ message count.

Part 2: Retry Strategy — Avoiding Poison Message Loops

The key insight: transient failures should be retried (abandon), but permanent failures should be dead-lettered immediately. Relying on MaxDeliveryCount alone means a poison message blocks a consumer for N retries before finally being moved to the DLQ.

The Retry Decision Matrix

Exception typeActionRationale
TransientException (network blip, throttling, DB timeout) abandon() Temporary — retrying may succeed. Let MaxDeliveryCount cap it.
FatalException (malformed payload, validation error) deadLetter() Will never succeed — no point retrying. Fail fast.
Unknown / unexpected deadLetter() after checking delivery count If it's already been retried N-1 times, dead-letter it early. 
ReliableProcessor.java
import com.azure.messaging.servicebus.*;
import com.azure.messaging.servicebus.models.*;
import java.time.Duration;

public class ReliableProcessor {

    private static final int MAX_MANUAL_RETRIES = 3;  // dead-letter after 3 manual retries

    private final ServiceBusProcessorClient processor;

    public ReliableProcessor(String connectionString, String queueName) {
        processor = new ServiceBusClientBuilder()
            .connectionString(connectionString)
            .processor()
            .queueName(queueName)
            .receiveMode(ServiceBusReceiveMode.PEEK_LOCK)
            .maxConcurrentCalls(10)
            .autoComplete(false)
            .processMessage(this::handleMessage)
            .processError(this::handleError)
            .buildProcessorClient();
    }

    private void handleMessage(ServiceBusReceivedMessageContext ctx) {
        ServiceBusReceivedMessage msg = ctx.getMessage();
        long deliveryCount = msg.getDeliveryCount();  // starts at 1

        try {
            processMessage(msg.getBody().toString());
            ctx.complete();

        } catch (TransientException e) {
            // Temporary — let it retry. But log delivery count for visibility.
            log.warn("Transient failure (attempt {}): {}", deliveryCount, e.getMessage());
            ctx.abandon();

        } catch (FatalException e) {
            // Permanent — dead-letter immediately, don't waste retries
            log.error("Fatal failure, dead-lettering: {}", e.getMessage());
            ctx.deadLetter(new DeadLetterOptions()
                .setDeadLetterReason("FatalProcessingError")
                .setDeadLetterErrorDescription(e.getMessage()));

        } catch (Exception e) {
            // Unknown — if near the limit, dead-letter early to save retries
            if (deliveryCount >= MAX_MANUAL_RETRIES) {
                ctx.deadLetter(new DeadLetterOptions()
                    .setDeadLetterReason("ExceededManualRetries")
                    .setDeadLetterErrorDescription(e.getMessage()));
            } else {
                ctx.abandon();
            }
        }
    }

    private void handleError(ServiceBusErrorContext ctx) {
        log.error("Processor error: {}", ctx.getException().getMessage());
        // The processor handles lock renewal and reconnects automatically.
        // Errors here are for visibility — no settlement needed.
    }

    public void start() { processor.start(); }
    public void close() { processor.close(); }
}
🧭 Pro tip: Set MaxDeliveryCount to a value high enough that transient failures get genuine retries, but low enough that poison messages don't clog the queue. For a typical microservice, 5–10 is reasonable. Set it when creating the queue: 
az servicebus queue update --resource-group myrg --namespace-name mysb \
    --name orders --max-delivery-count 5

Part 3: Duplicate Detection — Broker-Side

If your sender crashes after the broker accepts a message but before the client receives the acknowledgment, the sender doesn't know if the message was accepted. It resends — creating a duplicate. Duplicate detection solves this at the broker level.[source]

How It Works

  1. Enable duplicate detection on the queue or topic.
  2. Set a duplicate detection window (default 10 min, max 7 days).
  3. Set MessageId to a business-meaningful, deterministic value (e.g., order-12345).
  4. If the same MessageId is sent within the window, the broker discards the duplicate — but reports success to the sender.
// Configure on queue creation
az servicebus queue create \
  --resource-group myrg \
  --namespace-name mysb \
  --name orders \
  --enable-duplicate-detection true \
  --duplicate-detection-history-time-window PT10M   // ISO 8601: 10 minutes

// In Java, set MessageId deterministically
ServiceBusMessage message = new ServiceBusMessage(order.toJson())
    .setMessageId("order-" + order.getId());   // deterministic, business-keyed

sender.sendMessage(message)
    .doOnSuccess(v -> log.info("Sent (or duplicate-detected): {}", order.getId()))
    .subscribe();
Important caveats:
  • Partitioned entities use MessageId + PartitionKey for dedup, not just MessageId.
  • The detection window is a sliding window — it only remembers IDs within the last N minutes. Resending a message from 8 days ago won't be caught.
  • Duplicate detection impacts throughput — every send must check against the history. Keep the window as small as practical.
  • Scheduled messages are included in the detection window.

Part 4: Idempotent Consumers — The Client-Side Defense

Duplicate detection at the broker helps with send-side duplicates. But you also need consumer-side idempotency for when a message is delivered more than once (lock expiry + redelivery, at-least-once semantics).

Pattern: Processed-Message Registry

IdempotentConsumer.java
import java.util.concurrent.ConcurrentHashMap;

public class IdempotentConsumer {

    // In production, use Redis with TTL, not an in-memory map
    private final ConcurrentHashMap<String, Boolean> processedIds = new ConcurrentHashMap<>();

    private void handleMessage(ServiceBusReceivedMessageContext ctx) {
        String messageId = ctx.getMessage().getMessageId();

        // Check if already processed
        if (processedIds.putIfAbsent(messageId, true) != null) {
            log.info("Duplicate detected, skipping: {}", messageId);
            ctx.complete();   // still acknowledge to remove from queue
            return;
        }

        try {
            processMessage(ctx.getMessage().getBody().toString());
            ctx.complete();
        } catch (Exception e) {
            // On failure, remove from registry so retry can work
            processedIds.remove(messageId);
            ctx.abandon();
        }
    }
}

Pattern: Database Idempotency (Stronger)

// Use the message ID as an idempotency key in your database
// INSERT ... ON DUPLICATE KEY / ON CONFLICT DO NOTHING
@Transactional
public void processOrder(String orderJson, String messageId) {
    Order order = objectMapper.readValue(orderJson, Order.class);

    int inserted = jdbcTemplate.update(
        "INSERT INTO orders (id, data, idempotency_key) VALUES (?, ?::jsonb, ?) " +
        "ON CONFLICT (idempotency_key) DO NOTHING",
        order.getId(), orderJson, messageId
    );

    if (inserted == 0) {
        // Already processed — but DON'T throw, just acknowledge
        log.info("Idempotent skip: {}", messageId);
    }
}
🧭 The layered defense:

1. Broker duplicate detection — catches send-side duplicates (same MessageId within window)
2. Consumer idempotency — catches redelivery duplicates (lock expiry, abandon, at-least-once)
3. Database idempotency key — the final safety net, guarantees exactly-once processing

Putting It All Together: The Reliability Architecture

CompleteReliableService.java
import com.azure.messaging.servicebus.*;
import com.azure.messaging.servicebus.models.*;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Mono;
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;

@Service
public class OrderProcessingService {

    private final ServiceBusSenderAsyncClient sender;
    private final ServiceBusProcessorClient processor;
    private final IdempotencyStore idempotencyStore;  // Redis / DB

    public OrderProcessingService(
            @Value("${azure.servicebus.connection-string}") String connString,
            IdempotencyStore idempotencyStore) {

        ServiceBusClientBuilder builder = new ServiceBusClientBuilder()
            .connectionString(connString);

        this.sender = builder.sender().queueName("orders").buildAsyncClient();

        this.processor = builder.processor()
            .queueName("orders")
            .receiveMode(ServiceBusReceiveMode.PEEK_LOCK)
            .maxConcurrentCalls(10)
            .autoComplete(false)
            .processMessage(ctx -> processWithRetry(ctx))
            .processError(ctx -> log.error("Processor error", ctx.getException()))
            .buildProcessorClient();

        this.idempotencyStore = idempotencyStore;
    }

    // --- SEND: deterministic MessageId for duplicate detection ---
    public Mono<Void> sendOrder(Order order) {
        return sender.sendMessage(new ServiceBusMessage(order.toJson())
            .setMessageId("order-" + order.getId())      // broker dedup key
            .setContentType("application/json")
            .setSubject("order/created"));
    }

    // --- RECEIVE: idempotent processing with smart retry ---
    private void processWithRetry(ServiceBusReceivedMessageContext ctx) {
        ServiceBusReceivedMessage msg = ctx.getMessage();
        String messageId = msg.getMessageId();

        // Layer 1: Check if already processed (idempotency)
        if (idempotencyStore.alreadyProcessed(messageId)) {
            log.info("Skipping duplicate: {}", messageId);
            ctx.complete();
            return;
        }

        try {
            // Layer 2: Process with database-level idempotency
            Order order = parseOrder(msg.getBody().toString());
            boolean processed = idempotencyStore.processAtomically(messageId, order);

            if (processed) {
                ctx.complete();
                log.info("Processed: {}", messageId);
            } else {
                // Another instance already processed it
                ctx.complete();
            }

        } catch (TransientException e) {
            log.warn("Transient failure (attempt {}): {}", msg.getDeliveryCount(), e.getMessage());
            ctx.abandon();

        } catch (FatalException e) {
            log.error("Fatal failure, dead-lettering: {}", e.getMessage());
            ctx.deadLetter(new DeadLetterOptions()
                .setDeadLetterReason("FatalError")
                .setDeadLetterErrorDescription(e.getMessage()));

        } catch (Exception e) {
            if (msg.getDeliveryCount() >= 5) {
                ctx.deadLetter(new DeadLetterOptions()
                    .setDeadLetterReason("ExceededRetries")
                    .setDeadLetterErrorDescription(e.getMessage()));
            } else {
                ctx.abandon();
            }
        }
    }

    @PostConstruct
    public void start() { processor.start(); }

    @PreDestroy
    public void stop() {
        processor.close();
        sender.close();
    }
}

Key Takeaways

  • Dead-letter is NOT failure — it's visibility. A message in the DLQ has a reason code. Use it. Set up alerts on DLQ depth.
  • Differentiate transient vs. fatal failures. Abandon transient errors (let MaxDeliveryCount be the backstop). Dead-letter fatal errors immediately — don't waste retries.
  • Broker dedup ≠ consumer idempotency. Duplicate detection catches send-side duplicates. You still need idempotent consumers for receive-side redelivery. Always use an idempotency key in your database.
  • The detection window is short. Default 10 minutes, max 7 days. Design your MessageId around business keys so resends are deterministic even after the window closes.
  • DLQ messages don't auto-clean. You must explicitly process them. Build a DLQ monitoring and resubmission workflow.
