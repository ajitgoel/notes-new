Azure Service Bus Glossary

Quick reference for Service Bus terminology. Cross-referenced with concepts from other brokers.

Core Entities
Namespace
Top-level container for all Service Bus messaging entities (queues, topics). Equivalent to a "server" or "cluster" in other brokers, but fully managed. Each namespace gets its own capacity slice of a multi-tenant cluster. In Premium, isolated via Messaging Units.
Analogous to: RabbitMQ vhost, Kafka cluster
Queue
A durable message storage entity with FIFO ordering (time-stamped on arrival). Supports competing consumers where each message is processed by exactly one receiver. Messages are delivered in pull mode with long-polling support.
Analogous to: RabbitMQ queue, SQS queue
Topic
A publish-subscribe entity. Messages sent to a topic can be received by multiple subscriptions. Each subscription gets a copy of each message (subject to filters).
Analogous to: RabbitMQ exchange (fanout/topic type), Kafka topic (but with per-subscription cursor)
Subscription
A named entity attached to a topic that acts like a virtual queue. Receives copies of messages from the topic. Supports filters (SQL-like or correlation) to select which messages to receive, and optional actions to modify message metadata. Durable by default.
Analogous to: RabbitMQ queue bound to an exchange with a routing key, Kafka consumer group
Message Lifecycle
PeekLock receive mode
Two-stage receive: (1) Broker locks the message and returns it to the consumer, making it invisible to others. (2) Consumer calls Complete, Abandon, or DeadLetter to settle the message. Default lock duration is 60 seconds, max 5 minutes. Lock can be renewed.
Analogous to: RabbitMQ consumer acknowledgement (ack/nack), SQS visibility timeout
ReceiveAndDelete receive mode
Single-stage receive: message is marked as consumed immediately when sent to the client. Simpler but at-most-once — if the client crashes, the message is lost. No transactions or dead-lettering supported.
Complete settlement
Positive acknowledgment: consumer tells the broker the message was successfully processed. Message is permanently removed from the queue/subscription.
Analogous to: RabbitMQ basic.ack, SQS DeleteMessage
Abandon settlement
Negative acknowledgment: consumer tells the broker it cannot process the message. Lock is released immediately, making the message available for redelivery.
Analogous to: RabbitMQ basic.nack (requeue=true), SQS visibility timeout expiry
DeadLetter settlement
Consumer moves the message to the dead-letter queue (DLQ) — a built-in subqueue on every queue/subscription. Used when a message cannot be processed and retries won't help. A custom reason code can be attached.
Analogous to: RabbitMQ dead-letter exchange, SQS dead-letter queue
Advanced Features
Message Sessions
Enables strict FIFO processing within a session by grouping related messages with a SessionId. Only one consumer can hold the session lock at a time. Used for request-response patterns and ordered workflows.
Analogous to: Kafka partition (for ordering), but with an exclusive lock per session
Duplicate Detection
Broker-side deduplication based on MessageId. If a sender retries a send but the first attempt actually succeeded, the duplicate is discarded. Configurable time window (default 10 minutes, max 7 days).
Analogous to: Kafka idempotent producer, RabbitMQ publisher confirms (but broker-side, not client-side)
Scheduled Messages
Messages can be submitted for delayed processing — they become available for retrieval at a specific future time. Useful for job scheduling and retry with delay.
Message Deferral
A receiver can defer a message it receives if it cannot process it right now. The message is set aside but not lost — it can be retrieved later by its sequence number.
Autoforwarding
Automatically chains entities: a queue or subscription can forward messages to another queue or topic within the same namespace. Enables complex routing topologies.
Transactions
Atomic operations across multiple entities within the same namespace. Example: receive from Queue A, process, send to Queue B, and complete the original message — all atomically. Enables exactly-once processing patterns.
Tiers & Capacity
Standard Tier
Shared multi-tenant infrastructure. Variable latency and throughput. Pay-per-operation pricing. Message size up to 256 KB. Good for dev/test and low-throughput workloads.
Premium Tier
Dedicated, isolated resources via Messaging Units (MUs). Predictable latency and throughput. Fixed hourly pricing per MU. Message size up to 100 MB. Supports VNet/private endpoints, customer-managed keys, availability zones, JMS 2.0. Scale MUs up/down dynamically.
Messaging Unit (MU)
Unit of dedicated capacity in Premium tier. Each namespace gets 1–16 MUs. One MU ≈ ~4 MB/s throughput (ingress + egress). Monitor CPU usage: scale up if >70%, scale down if <20%.
Protocols & SDKs
AMQP 1.0
The primary wire protocol for Service Bus. Open ISO/IEC standard. Enables efficient, persistent connections with batching, prefetch, and async pipelining. Also used by RabbitMQ and ActiveMQ. SBMP is being retired 30 September 2026.
Azure.Messaging.ServiceBus SDK
The modern .NET SDK (NuGet). Replaces Microsoft.Azure.ServiceBus and WindowsAzure.ServiceBus. Uses AMQP by default. Clients (ServiceBusClient, ServiceBusSender, ServiceBusReceiver, ServiceBusProcessor) are designed as singletons — reuse them, don't create per-message.
Comparison: Service Bus vs. Other Azure Services
Service Bus vs. Storage Queues
Storage Queues are simpler, cheaper, and larger (up to 80 GB queues). Service Bus supports topics, sessions, transactions, duplicate detection, dead-lettering, and 100 MB messages (Premium). Use Storage Queues for simple, high-volume message storage; Service Bus for enterprise messaging with advanced features.
Service Bus vs. Event Hubs
Event Hubs is for event streaming at massive scale (millions/sec). It uses a partitioned consumer model where consumers track their own offset. Service Bus is for enterprise messaging with per-message settlement, sessions, and transactions. Event Hubs = firehose of events; Service Bus = reliable message broker.
Service Bus vs. Event Grid
Event Grid is for reactive event distribution — push-based, serverless, at-least-once. It routes events from Azure resources to subscribers (Functions, webhooks). Service Bus uses pull with settlement. Event Grid = event notification; Service Bus = message processing with guarantees.
