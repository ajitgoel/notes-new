Lesson 05 / 08 Backpressure: Controlling the Flow

Backpressure is the mechanism by which a slow consumer signals a fast producer to slow down — or to discard/buffer excess items. Without it, a fast producer overwhelms a slow consumer, causing out-of-memory errors or data loss. This is the fundamental property that makes Reactor more than just "async streams".

Backpressure Strategies

BUFFER

Queue excess items until consumer catches up. Risk: unbounded memory growth. Use with a size limit.

DROP

Discard items that arrive when consumer isn't ready. Lossy — only use when missing items is acceptable.

LATEST

Keep only the most recent item; overwrite buffered item on each new arrival. Good for sensor/telemetry data.

ERROR

Throw OverflowException when the buffer is full. Fail-fast: makes the overflow visible immediately.

Applying Backpressure Strategies in Reactor

import reactor.core.publisher.FluxSink;
import reactor.core.publisher.BackpressureStrategy;

// Strategy 1: BUFFER — queue up to N items
Flux<DrugEvent> events = serviceBusSource
    .onBackpressureBuffer(1000);  // buffer up to 1000, then OverflowException

// Strategy 2: DROP — silently discard overflow
Flux<AuditEvent> audit = highVolumeSource
    .onBackpressureDrop(dropped ->
        log.warn("Audit event dropped: {}", dropped.getId()));

// Strategy 3: LATEST — keep only newest item
Flux<InventoryLevel> inventory = inventoryStream
    .onBackpressureLatest();

// Strategy 4: ERROR — fail immediately on overflow
Flux<Order> orders = orderStream
    .onBackpressureError();  // OverflowException if consumer too slow

// Strategy 5: Custom with FluxSink (for bridging non-reactive sources)
Flux<PharmacyEvent> custom = Flux.create(
    sink -> legacyEventSource.onEvent(e -> sink.next(e)),
    FluxSink.OverflowStrategy.DROP
);

limitRate: Pull-Based Flow Control

limitRate is the cleanest backpressure tool — it controls how many items the subscriber requests at a time:

// Request at most 100 items at a time, refill when 75% consumed (25% threshold)
prescriptionStream
    .limitRate(100)     // prefetch=100, replenish trigger at 75
    .flatMap(this::processPrescription);

// limitRate with low/high watermarks
prescriptionStream
    .limitRate(100, 20)   // request 100, re-request when 20 remain
    .flatMap(rx -> drugCheckService.verify(rx), 8);  // concurrency=8

Backpressure in Service Bus Processing

For Empower PMS's Azure Service Bus consumer, you want bounded concurrency and controlled prefetch:

@Service
public class PrescriptionEventConsumer {

    @Bean
    public Consumer<Flux<ServiceBusReceivedMessageContext>> processRxEvents() {
        return messages -> messages
            // Control how fast we pull from Service Bus
            .limitRate(50)

            // Process with bounded concurrency (don't spawn unlimited threads)
            .flatMap(
                ctx -> processMessage(ctx.getMessage()),
                10  // max 10 concurrent message processings
            )

            .doOnError(ex -> log.error("Consumer error", ex))
            .subscribe();  // Reactor auto-manages for @Bean Consumer
    }

    private Mono<Void> processMessage(ServiceBusReceivedMessage msg) {
        return Mono.fromCallable(() -> deserialize(msg))
            .flatMap(rxEvent -> rxService.process(rxEvent))
            .then();
    }
}
The flatMap concurrency parameter
flatMap(fn, concurrency) — the second argument is your backpressure knob. Without it, Reactor uses Integer.MAX_VALUE (unlimited parallelism). For pharmacy fill events, concurrency=10-20 is a reasonable starting point and prevents DB connection pool exhaustion.
