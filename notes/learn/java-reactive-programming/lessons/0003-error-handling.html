Lesson 03 / 08 Error Handling in Reactive Streams

In a reactive stream, an error is a terminal signal. When onError(Throwable) fires, the stream ends — no more onNext calls. This is fundamentally different from try/catch, because errors travel downstream through the operator chain. This lesson is what separates production-grade reactive code from demo code.

Don't Do This
Never put a try/catch inside a flatMap or map lambda and swallow exceptions. This leaves you with silent failures and orphaned streams. Let errors propagate through the reactive channel and handle them with dedicated operators.

The Error Propagation Model

patientRepo.findById(id) → onNext(patient)
formularyService.check(patient) → throws FormularyException
onError(FormularyException) ← error signal propagates DOWN
flatMap(rx -> repo.save(rx)) ← SKIPPED — stream terminated
eventBus.publish(...) ← SKIPPED
onErrorResume / onErrorReturn ← handles here, OR subscriber.onError()

The Three Error Strategies

onErrorReturn

Return a fallback value. Stream completes normally after the fallback.

onErrorResume

Switch to a fallback publisher. Can do async recovery (another DB lookup, another service).

onErrorMap

Transform the exception type. Useful for converting infra exceptions to domain exceptions.

retry / retryWhen

Re-subscribe and replay the entire upstream. For transient failures (network, Service Bus).

onErrorReturn — synchronous fallback value

// If formulary service fails, return a default coverage object
formularyService.getCoverage(patientId, ndc)
    .onErrorReturn(Coverage.defaultCoverage());

// Target a specific exception type
formularyService.getCoverage(patientId, ndc)
    .onErrorReturn(FormularyTimeoutException.class, Coverage.defaultCoverage());
// Other exception types will still propagate as errors

onErrorResume — async fallback publisher

// Primary: live formulary API. Fallback: cached value from Redis.
formularyService.getCoverage(patientId, ndc)
    .onErrorResume(ex -> {
        log.warn("Formulary API down, using cache: {}", ex.getMessage());
        return redisCache.getCoverage(patientId, ndc);  // returns Mono<Coverage>
    });

// Handle different exceptions differently
repo.findById(id)
    .onErrorResume(NotFoundException.class,
        ex -> Mono.error(new ResponseStatusException(NOT_FOUND, ex.getMessage())))
    .onErrorResume(DataAccessException.class,
        ex -> Mono.error(new ServiceUnavailableException("DB")));

onErrorMap — translate exceptions

// Don't leak infrastructure exceptions to the API layer
rxRepo.save(prescription)
    .onErrorMap(DataIntegrityViolationException.class,
        ex -> new DuplicatePrescriptionException(prescription.getId()))
    .onErrorMap(TransientDataAccessException.class,
        ex -> new RetryableException("DB transient failure", ex));

Retry: For Transient Failures

Azure Service Bus calls, HTTP to external APIs, and SQL Server connections can have transient failures. Don't let them fail the stream — retry with exponential backoff.

import reactor.util.retry.Retry;
import java.time.Duration;

// Simple: retry up to 3 times immediately
serviceBusClient.sendMessage(event)
    .retry(3);

// Production: exponential backoff with jitter
serviceBusClient.sendMessage(event)
    .retryWhen(Retry.backoff(3, Duration.ofMillis(200))
        .maxBackoff(Duration.ofSeconds(5))
        .jitter(0.5)
        .filter(ex -> ex instanceof TransientServiceBusException)
        .onRetryExhaustedThrow((spec, signal) ->
            new ServiceBusUnavailableException("After 3 retries", signal.failure())));

// IMPORTANT: retry re-subscribes to the WHOLE upstream
// If the DB lookup is also in the chain, it will run again too
// Use .retryWhen() only on the specific operation that needs it
Pharmacy Production Pattern
For Azure Service Bus publish failures in Empower PMS: use retryWhen with backoff on the publish step only — not the entire prescription fill pipeline. Wrap just the eventBus.publish() call in its own reactive chain with retry.

doOnError — Observe Without Handling

// Log errors WITHOUT consuming them — they still propagate
prescriptionPipeline
    .doOnError(ex -> log.error("Fill failed: patientId={}", patientId, ex))
    .onErrorResume(ex -> Mono.error(new FillException("Fill failed", ex)));
// doOnError fires THEN the error continues downstream

Complete Error-Resilient Pipeline

public Mono<FillConfirmation> fillWithResilience(FillRequest req) {
    return patientRepo.findById(req.patientId())

        // Convert infra ↦ domain exception at the boundary
        .onErrorMap(DataAccessException.class,
            ex -> new PatientLookupException(req.patientId(), ex))

        .flatMap(patient ->
            formularyService.getCoverage(patient, req.ndc())

                // Formulary timeout → cached coverage
                .onErrorResume(FormularyTimeoutException.class,
                    ex -> redisCache.getCoverage(patient, req.ndc()))
                .map(cov -> buildRx(patient, cov, req))
        )

        .flatMap(rx -> rxRepo.save(rx)
            .retryWhen(Retry.backoff(2, Duration.ofMillis(100))
                .filter(e -> e instanceof TransientDataAccessException))
        )

        .flatMap(saved -> eventBus.publish(new RxFilledEvent(saved))
            .retryWhen(Retry.backoff(3, Duration.ofMillis(200)))
            .onErrorResume(ex -> {
                log.error("Event publish failed, fill succeeded: {}", saved.getId());
                return Mono.empty(); // don't fail fill if event fails
            })
            .thenReturn(saved)
        )

        .map(FillConfirmation::from)

        .doOnError(ex -> metrics.increment("fill.error", "type", ex.getClass().getSimpleName()));
}
