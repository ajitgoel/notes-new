Lesson 04 / 08 Schedulers & Threading

Reactive code doesn't automatically run on the right thread — you decide where each part of a pipeline executes. Get this wrong and you'll block event-loop threads (killing throughput) or starve bounded thread pools (killing parallelism). This is where Reactor's Schedulers come in.

The Scheduler Types

Scheduler Thread pool Use for
Schedulers.parallel() Fixed, CPU-count threads CPU-bound work: transformations, in-memory computation. Non-blocking only
Schedulers.boundedElastic() Elastic, capped (10× CPU) Blocking I/O that can't be made reactive: legacy JDBC, file I/O, blocking HTTP clients. Blocking OK
Schedulers.single() Single thread, reused Serialized work, periodic tasks. Not for blocking.
Schedulers.immediate() Caller's thread Testing. Synchronous execution on the current thread.
Schedulers.fromExecutor(exec) Your executor Custom thread pools (e.g. Spring's task executor).

subscribeOn vs publishOn

These two operators are the most misunderstood in Reactor. They do different things:

subscribeOn
subscribeOn(scheduler) — affects where the subscription (source creation) happens. Controls the thread that runs the upstream source. Only the first subscribeOn matters; later ones are ignored.
publishOn
publishOn(scheduler) — affects everything downstream from where it appears. Switches the thread for all subsequent operators until another publishOn.

// Pattern: blocking legacy JDBC with subscribeOn
Mono<List<Patient>> patients = Mono.fromCallable(
        () -> legacyJdbcRepo.findAll()  // blocking call
    )
    .subscribeOn(Schedulers.boundedElastic());
// The JDBC call runs on boundedElastic, freeing the event-loop thread

// Pattern: CPU transform on parallel scheduler
prescriptions
    .publishOn(Schedulers.parallel())
    .map(rx -> heavyCryptoSignature(rx))    // CPU-bound, runs on parallel pool
    .publishOn(Schedulers.boundedElastic())
    .flatMap(rx -> rxRepo.save(rx));         // DB on elastic pool
Never Block an Event Loop Thread
If your code runs on a Netty/Reactor event-loop thread (e.g. in a WebFlux handler) and you call a blocking method directly — Thread.sleep(), JDBC, Future.get() — you'll starve the event loop. All incoming requests on that reactor thread stall. Use Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic()) to escape to a blocking-safe pool.

Reactor's BlockHound

Reactor ships BlockHound — a Java agent that detects blocking calls on non-blocking threads at runtime. Install it in your test profile:

// pom.xml (test scope)
<dependency>
  <groupId>io.projectreactor.tools</groupId>
  <artifactId>blockhound</artifactId>
  <version>1.0.8.RELEASE</version>
  <scope>test</scope>
</dependency>

// In your test setup or main():
BlockHound.install();
// Throws BlockingOperationError if a blocking call happens on a reactor thread
// Add to Spring Boot tests — catches violations immediately

Wrapping Blocking Code: The Empower Pattern

Empower PMS currently uses a blocking SQL Server JDBC driver while R2DBC support is being added. Here's the correct pattern for wrapping it:

@Service
public class LegacyPatientAdapter {

    private final PatientJdbcRepository jdbcRepo;

    // Wrap blocking JDBC in a reactive publisher
    public Mono<Patient> findById(Long id) {
        return Mono.fromCallable(() -> jdbcRepo.findById(id)
                .orElseThrow(() -> new PatientNotFoundException(id)))
            .subscribeOn(Schedulers.boundedElastic());
    }

    // For collections
    public Flux<Patient> findByFacility(String facilityCode) {
        return Mono.fromCallable(() -> jdbcRepo.findByFacilityCode(facilityCode))
            .subscribeOn(Schedulers.boundedElastic())
            .flatMapMany(Flux::fromIterable);
    }
}
