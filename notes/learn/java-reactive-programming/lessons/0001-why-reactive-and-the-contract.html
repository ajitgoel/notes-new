Lesson 01 / 08 Why Reactive & The Publisher/Subscriber Contract

The Problem With Blocking

Consider a prescription request hitting your Empower PMS API. It must: validate the patient, check drug interactions, call a formulary service, persist the record, and publish an event to Azure Service Bus. On a traditional thread-per-request model, a single Tomcat thread is parked for every one of those network calls — doing nothing, consuming 512KB of stack, waiting.

⛔ Blocking / Imperative

// Thread is BLOCKED here
Patient p = db.findPatient(id); // ~5ms wait
Drug d = formulary.lookup(ndc); // ~20ms wait
repo.save(prescription);          // ~8ms wait
bus.publish(event);               // ~15ms wait
// 200 concurrent requests = 200 parked threads

✅ Reactive / Non-blocking

// Thread is NEVER parked — it returns
// to the pool between each step
findPatient(id)
  .flatMap(p -> lookup(p.ndc()))
  .flatMap(d -> repo.save(rx))
  .flatMap(saved -> bus.publish(event));
// 200 concurrent requests, ~8 threads
Key Insight
Reactive doesn't make individual operations faster. It makes the JVM able to handle dramatically more concurrent operations with the same hardware, because threads are never idle-waiting.

The Reactive Streams Specification

Before Project Reactor, before RxJava — there's a 4-interface spec every reactive library implements. It lives at reactive-streams/reactive-streams-jvm and was folded into Java 9 as java.util.concurrent.Flow.

// The 4 interfaces of the Reactive Streams spec
public interface Publisher<T> {
    void subscribe(Subscriber<? super T> subscriber);
}

public interface Subscriber<T> {
    void onSubscribe(Subscription s);   // called first, gives you the tap
    void onNext(T item);                  // called for each item
    void onError(Throwable t);            // terminal — no more items
    void onComplete();                    // terminal — stream exhausted
}

public interface Subscription {
    void request(long n);  // downstream pulls n items — backpressure!
    void cancel();
}

public interface Processor<T, R> extends Subscriber<T>, Publisher<R> {}

The protocol is a handshake

Nothing flows until Subscription.request(n) is called. That's the key to backpressure — a downstream that's slow can tell the upstream "give me only 10 items" rather than drowning.

Reactor's Two Types: Mono and Flux

Project Reactor is Spring's implementation of the Reactive Streams spec. It gives you two publisher types you'll use constantly:

// Mono — 0 or 1 item. Like Optional but async.
Mono<Patient>   // "I will eventually produce a Patient, or nothing, or an error"
Mono<Void>     // "I will signal completion (or error), emit nothing"

// Flux — 0 to N items. Like Stream but async + backpressure-aware.
Flux<Prescription>  // "I will stream N prescriptions"
Flux<DrugEvent>     // "I will stream events from Azure Service Bus forever"
Critical Rule
Nothing happens until you subscribe. A Mono or Flux is a description of a computation — a recipe. Calling findPatient(id) that returns a Mono<Patient> does not hit the database. Only .subscribe() (or Spring WebFlux's framework subscribe) triggers execution.

Your first Mono and Flux

import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

// Creating publishers
Mono<String> greeting = Mono.just("Hello, Empower");
Mono<String> empty    = Mono.empty();
Mono<String> failed   = Mono.error(new RuntimeException("no patient"));

Flux<Integer> nums    = Flux.just(1, 2, 3, 4, 5);
Flux<Integer> range   = Flux.range(1, 100);

// Nothing happens yet. Add a subscriber:
greeting.subscribe(
    value -> System.out.println("Got: " + value),
    error -> System.err.println("Error: " + error),
    ()    -> System.out.println("Done")
);
// Output: Got: Hello, Empower
//         Done
Spring WebFlux Note
In a Spring WebFlux controller, you return the Mono or Flux — Spring subscribes for you. You will almost never call .subscribe() manually in application code. The subscription is the framework's job.

Cold vs Hot Publishers

This trips up almost every developer new to reactive:

// COLD publisher — each subscriber gets their own execution
Mono<Patient> dbLookup = patientRepo.findById(id);
// Subscriber A → triggers a DB query
// Subscriber B → triggers ANOTHER DB query (independent execution)

// HOT publisher — shares a single execution with all subscribers
Flux<DrugEvent> eventStream = serviceBusReceiver.receiveMessages();
// Both subscriber A and B see the SAME messages
// A message is not replayed for late subscribers

Most reactive sources you'll create (DB queries, HTTP calls) are cold. Azure Service Bus event streams are hot. You'll need .share() or .publish() to multicast a cold source.

KNOWLEDGE CHECK

You write: Mono<Patient> m = patientRepo.findById(123L); — and then do nothing else. How many database queries have been executed?

In your Empower PMS WebFlux controller, you return a Mono<ResponseEntity<Prescription>>. Who calls .subscribe()?

Which type would you use to represent "find a patient by ID" — where the patient may or may not exist?
